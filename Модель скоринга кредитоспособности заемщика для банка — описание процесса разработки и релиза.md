## 1. Выбор Git-стратегии

### Стратегия: Git Flow

Для команды, разрабатывающей модель кредитного скоринга, Git Flow является оптимальным выбором. Обоснование:

- **Размер команды**: гипотетически 5–10 человек: data scientists, ML-инженеры, аналитики. Требуется чёткое разделение разработки новых фич, подготовки релизов и срочных исправлений.
- **Критичность системы**: модель влияет на финансовые решения, поэтому стабильность и возможность быстрого исправления ошибок (hotfix) критичны.
- **Частота релизов**: невысокая (раз в несколько недель или месяцев), но с возможностью внеочередных патчей. Git Flow позволяет вести долгоживущие ветки разработки (`develop`), изолировать подготовку релиза (`release/`) и оперативно чинить критические проблемы (`hotfix/`).
- **Параллельная разработка**: несколько фич могут разрабатываться одновременно в feature-ветках, не влияя на стабильность основной ветки.

Основные ветки:
- `main` — только готовый к продакшену код, каждый коммит здесь соответствует релизному тегу.
- `develop` — интеграционная ветка для завершённых фич.
- `feature/*` — для разработки новых функций.
- `release/*` — для финальной подготовки релиза.
- `hotfix/*` — для срочных исправлений в продакшене.

## 2. Описание релизного цикла

### 2.1. Выпуск первого релиза v1.0.0

1. **Инициализация репозитория**: созданы ветки `main` и `develop`. В `main` — заготовка (README, лицензия).
2. **Разработка baseline-модели**:
   - От `develop` создаётся ветка `feature/baseline-model`.
   - Разработчики добавляют код предобработки, обучения, инференса.
   - После завершения создаётся Pull Request (PR) в `develop`, проходят ревью и автоматические проверки (CI).
   - Вливание в `develop`.
3. **Подготовка релиза**:
   - От `develop` создаётся ветка `release/v1.0.0`.
   - В ней проводят финальное тестирование, обновляют документацию, CHANGELOG.
   - Все исправления вносятся непосредственно в `release/v1.0.0`.
4. **Релиз**:
   - Ветка `release/v1.0.0` вливается в `main` и `develop`.
   - На коммите в `main` создаётся аннотированный тег `v1.0.0`.
   - На GitHub создаётся Release с описанием (например, "Первый стабильный релиз модели кредитного скоринга").
5. **Развёртывание**: CI/CD пайплайн автоматически разворачивает модель в тестовой среде, затем после проверки — в продуктивной.

### 2.2. Исправление утечки данных (data leak) — v1.0.1

1. Обнаружено, что в процессе обучения использовались признаки, недоступные в момент предсказания (например, информация о будущем поведении клиента).
2. Создаётся ветка `hotfix/1.0.1-data-leak` от `main`.
3. Вносятся изменения в код: корректируется пайплайн признаков, переобучается модель.
4. В коммитах используется тип `fix`.
5. После завершения создаётся PR в `main` и `develop`.
6. После ревью и успешного CI ветка вливается в обе ветки.
7. На `main` создаётся тег `v1.0.1` и релиз с описанием исправления.
8. Обновлённая модель проходит верификацию и деплоится.

### 2.3. Добавление нового мощного признака — v1.1.0

1. Команда Data Science разрабатывает новый признак (например, скоринговый балл из внешнего источника), который значительно улучшает метрики.
2. От `develop` создаётся ветка `feature/new-external-score`.
3. Разработка включает изменения в коде, тесты, обновление конфигов.
4. Коммиты: `feat: add external credit bureau score`.
5. Создаётся PR в `develop`, проходит ревью, проверки CI.
6. После вливания в `develop` начинается подготовка минорного релиза: создаётся ветка `release/v1.1.0`.
7. В ней проверяются метрики, обновляется CHANGELOG (добавляется секция для v1.1.0).
8. Вливание в `main` и `develop`, тег `v1.1.0`, релиз.
9. Модель с новым признаком деплоится после успешной верификации.

### 2.4. Кардинальное изменение выхода модели — v2.0.0

Бизнес решает, что модель должна не только выдавать вероятность дефолта, но и объяснять причины (например, ключевые факторы, повлиявшие на решение).

1. Изменения затрагивают API, формат вывода, возможно, архитектуру модели. Это мажорная версия.
2. Работа ведётся в долгоживущей ветке (или нескольких feature-ветках), которые вливаются в `develop`.
3. Примеры коммитов: `feat: add explainability module`, `refactor: change prediction output to include feature contributions`.
4. После завершения всех фич создаётся ветка `release/v2.0.0`.
5. Проводится комплексное тестирование, обновляется документация для пользователей.
6. Вливание в `main` и `develop`, тег `v2.0.0`.
7. Релиз сопровождается подробным описанием изменений, возможно, обучением пользователей.
8. Развёртывание новой версии может потребовать миграции данных и обновления интеграций.

## 3. Примеры сообщений коммитов и CHANGELOG

### 3.1. Примеры коммитов

- **feat**: `feat: add income verification feature from tax database`
- **fix**: `fix: resolve data leakage from target encoding in train set`
- **docs**: `docs: update API usage examples in README`
- **refactor**: `refactor: unify feature scaling logic across preprocessing modules`

## 4. Проектирование CI/CD Pipeline

Для каждого коммита в feature-ветку запускается следующий конвейер:

1. **Линтер и форматтер**: `flake8`, `black`, `isort` — проверка стиля кода.
2. **Статический анализ типов**: `mypy` — выявление потенциальных ошибок типов.
3. **Unit-тесты**: `pytest` с покрытием ключевых модулей (препроцессинг, вычисление признаков, загрузка данных).
4. **Тесты на небольших данных**: запуск пайплайна обучения на синтетическом или малом наборе данных для быстрой проверки целостности.
5. **Тесты на уязвимости**: `bandit` или `safety` для проверки зависимостей.
6. **Сборка артефакта**: создание Docker-образа с моделью и зависимостями, сохранение его в реестре (например, GitHub Container Registry) с тегом `feature-xxx`.
7. **(Опционально) Интеграционные тесты**: запуск контейнера и проверка ответов API на корректность.

Для веток `develop` и `main` дополнительно могут запускаться более полные тесты, включая проверку метрик на валидационном наборе и нагрузочное тестирование.

## 5. Чек-лист верификации (UV) перед релизом

Перед выпуском любой версии модели (особенно в продакшен) необходимо пройти по следующим пунктам:

### 5.1. Метрики качества
- [ ] AUC-ROC на тестовой выборке за последний квартал не ниже 0.85.
- [ ] Precision для top-5% самых рискованных заёмщиков > 0.7.
- [ ] Recall для дефолтных случаев > 0.6.
- [ ] Калибровка вероятностей (Brier score) в допустимых пределах.
- [ ] Стабильность метрик на временных срезах (backtesting).

### 5.2. Производительность
- [ ] Среднее время инференса одного запроса < 100 мс.
- [ ] Использование памяти при пиковой нагрузке не превышает 2 ГБ.
- [ ] Модель успевает обрабатывать планируемый RPS (запросов в секунду) без таймаутов.

### 5.3. Проверка данных
- [ ] Мониторинг дрифта признаков: распределения ключевых признаков на новых данных не отличаются от обучающих более чем на порог (PSI < 0.1).
- [ ] Проверка наличия пропусков: модель корректно обрабатывает пропуски (заполнение средним/медианой или отказ).
- [ ] Типы входных данных соответствуют ожидаемым (схема данных утверждена).

### 5.4. Безопасность и стабильность
- [ ] Модель устойчива к аномальным значениям (не падает, выдаёт обоснованный скор).
- [ ] Проверена защита от состязательных атак (например, не меняется решение при незначительных вариациях входа).
- [ ] Код не содержит секретов (ключей, паролей) — проверено сканером.
- [ ] Модель проходит внутренний аудит на соответствие регуляторным требованиям (например, объяснимость для заёмщика).

После успешного прохождения всех пунктов создаётся релизный тег и модель отправляется в продуктивную среду.
